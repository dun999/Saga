Privacy & cookies

Last updated: 8 October 2026

A memory namespace is a label, not a login or a password. Anyone entering the same guest username shares its memory, chats and workspace files.

Access to connected accounts depends on the server's account mode. Host account mode shares the machine's agent logins. User account mode keeps personal credentials tied to a verified wallet or a password-protected username.

Memory is encrypted for storage on Walrus, but Saga, its memory relayer and the AI services processing your requests can read the content they receive.

User account mode
Personal accounts for each wallet		Only a verified wallet or a username signed in with its password can save personal credentials. Saga uses a separate credential key and provider home for each wallet and provider. A different wallet cannot inherit a connection by reusing a name or memory namespace. Guests cannot connect personal accounts in this mode. Signing in with the same wallet represents the same identity; remembered connections can be reused after unlocking the same vault key.

Example: Alex enters guest username A and connects Claude Code in host account mode. Blair enters A and can use that Claude account and see A's history. Entering B selects different guest memory, but still allows use of the same host Claude account. Switching to a wallet alone does not change the server's account mode.

For an operator serving multiple people, Saga requires user account mode, sign-in for every request (a wallet, or a username with a password), HTTPS and sandbox configuration. The account flag is --accounts user; --wallet-only turns username sign-in off. The built-in @saga assistant still uses the operator's inference account.

Wallet or guest

  • Wallet. A signature proves control of your Sui address. Saga uses it to restrict access through the app to that identity's memory and personal connections. This does not make your data inaccessible to the server operator or the services processing it.
  • Guest username. Anyone who enters the same username sees and adds to its memory, chats and files. Guest names are normalized, so changing letter case does not create a separate identity. Don't put private information in a guest session.

Who runs this

Saga is open-source software built for the Walrus “Chatbots That Remember” hackathon. Each deployment is run by its operator — whoever hosts the server you are using. This page describes the software's behavior. The operator controls the server, configuration, logs and backups, and can access data processed there. Ask that operator about its retention and backup practices.

Memory ownership and access. Saga uses the deployment's configured MemWal account to store and recall memory, with namespaces for each Saga identity. Signing in with a wallet does not automatically make that wallet the owner of a separate MemWal account. The operator's memory credentials can access the deployment's stored memories. See MemWal's trust and security model.

Secret redaction has limits. Saga filters known credentials and recognizable secret patterns before memory writes. It cannot guarantee detection of every secret. Prompts and recall queries also leave Saga for processing. Don't paste credentials into chats or files intended for memory; use the connection controls.

Recalled memories. A turn's “View sources” panel shows selected excerpts, blob IDs and retrieval details. Those records are saved with the chat, so removing an original source alone does not remove copies in transcripts or other derived memories. The panel shows what Saga retrieved, not proof that a model used every source.

In user account mode, sandboxed CLI agents can request additional memory searches, including saved chat transcripts. Saga restricts each run to the signed-in identity's content namespaces and records these searches with the turn. The deployment's memory key stays on the server.

Saved transcripts retain up to 4,000 bytes of each user message and 6,000 bytes of each agent response after redaction. Longer entries are marked as shortened. Failed steps can retain both their partial response and error. File checkpoints are partial snapshots and may omit file contents when size limits apply.

Your connected accounts

The vault protections below apply to personal connections saved through Saga. They do not apply to the host machine's CLI logins.

  • Encrypted between uses. Saga seals credentials with XSalsa20-Poly1305 using keys derived from your wallet signature (or, for a username, from its password with Argon2id) and separated by account and provider. A username's password is kept only as an Argon2id verifier in the server's private key file, never in memory. Metadata such as the wallet address, provider name, credential type, remember choice and a vault-key fingerprint can remain unencrypted.
  • Temporary tool files. In user account mode, Saga seals CLI sign-ins and cleans provider homes after the last active call. Tools can write plaintext credentials, prompts, transcripts, logs and caches while running. A crash or cleanup failure can leave files until cleanup runs; chat workspaces and server backups are not erased by this cleanup.
  • Your choice to remember. New personal connections last until sign-out, session expiry or server restart. Their encrypted credentials stay in memory between operations. Choosing “Remember this account on this server” retains encrypted credentials on disk for future sessions. Host CLI logins are not governed by this choice.
  • Server access while unlocked. The vault key stays in server memory during an unlocked session and active operations. Saga decrypts credentials when needed. In user account mode, a CLI sees its own provider home inside its sandbox. These protections still require trust in the operator.
  • Disconnect and revocation differ. Disconnect removes the personal credential from Saga's active storage. It does not delete the provider account or necessarily revoke the token at the provider. Saga attempts GitHub OAuth revocation when it has the required app credentials and reports failure; otherwise, revoke access in the provider's settings.
  • Some wallets can't recreate the key. Wallets that sign with rotating keys (for example Google sign-in wallets) may produce a different vault key on a new device. Saga can't open what was sealed before, and asks you to reconnect.

Third parties

Using Saga involves these services, each under its own terms and privacy policy:

  • MemWal relayer and its processing services — receive memory content and search queries for extraction, embeddings, encryption and recall. Walrus stores encrypted blobs. The relayer's service configuration determines which additional processing providers it uses.
  • Sui GraphQL — receives the address, signed message and signature for wallet types Saga cannot verify locally. The default endpoint is on mainnet.
  • Boundless inference — the default built-in @saga agent sends it prompts and selected memories through the operator's account, including in user account mode.
  • AI providers — Anthropic, OpenAI, xAI and configured API endpoints receive prompts, selected memories and any file or tool content the agents send. Depending on the agent and mode, this uses your personal connection or the operator's account. Provider retention and training policies apply separately.
  • GitHub — receives sign-in requests and authenticated API or git operations when you connect it. Repo clones stay on the Saga server; pushes and pull requests send content to GitHub.
  • esm.sh and Google Fonts — supply the app's wallet library and app or landing-page fonts. Your browser contacts these services and exposes ordinary request information, including its IP address.
  • Walruscan and other external links — opening a blob link sends its identifier to the explorer. External sites have their own data practices.

Deleting your data

  • Chat history: use the trash button beside a chat to remove it from your history on this server. Saved facts, corrections, lessons, workspace files, checkpoints and archived Walrus transcripts are kept. Agents can still recall saved memory. A deletion marker in the server's Saga config directory keeps the chat hidden across browsers and restarts; the operator must preserve these markers when moving or restoring the server. This action does not erase stored blobs.
  • Personal credentials: use Profile → Connections → Disconnect, or remove a custom API agent. This removes its saved credential from Saga's active storage. It does not erase chats, cloned repos, backups or data already sent to providers. Revoke API keys and authorizations at the provider when needed.
  • Host connections: Disconnect runs the provider's sign-out on the host machine and affects other users of that CLI. Signing out of Saga alone does not sign the host's CLI out.
  • Wallet session: use Profile → Sign out to invalidate that session, clear its vault key and cancel active work. Clearing cookies alone does not immediately revoke a session on the server or stop running work; the session expires after one hour of inactivity, or seven days after sign-in even if it is in use. Signing out of a guest name does not delete its shared data.
  • Memory and files: Saga has no in-app delete-all-memory control. Ask the operator to remove local workspaces and arrange deletion of stored memory, including transcripts, source copies and shared corrections. Removing search-index entries alone does not erase Walrus blobs; restoration can make them searchable again.
  • Walrus retention: deletion depends on blob ownership and the relayer's available controls. MemWal documents a Security Delete flow for eligible blobs, authorized by their owning wallet; in Saga that may be the deployment's memory-account owner. Storage expiry is not a promise that every copy disappears. Provider records and operator backups have separate retention.
